# ADR-0007: PR の検査は公開ワークフローと同じ1ファイルで走らせ、Ruleset でマージを止める

- **状態**: 有効
- **決定日**: 2026-09-13
- **関連**: Issue #23 / [ADR-0005](./0005-page-completion-check.md)（検査を `npm test` 1本にまとめた理由） / [`CONTRIBUTING.md`](../../CONTRIBUTING.md)「ガードレール」

## 背景（何に困っていたか）

`CONTRIBUTING.md` は「PR を開く → CI が緑 → Squash merge」と書き、ガードレール表には
「CI: PR 時にビルドが壊れたままのマージを防ぐ」「ブランチ保護（Ruleset）」とあった。
ところが 2026-09-13 時点の実態は、ワークフローが `deploy.yml` の1本だけで **`main` への push
でしか動かず**、`main` に Ruleset も従来型の保護も**無かった**。PR #21・#22 はどちらも
チェック0件のままマージできた。

つまり守りはローカルの pre-push フックと「PR 前に自分で `npm test` を回す」習慣だけ。
忘れれば壊れたまま `main` に入り、公開のデプロイが落ちて初めて気づく。

制約:

- 検査の実体は `npm test` 1本（ADR-0005）。PR 時と公開時で**同じ手順**が走ることが要る
- ワークフローは4ステップしかなく、仕組みを増やすほど割に合わない
- public リポジトリなので Ruleset は無料で使える

## 決定

1. **`deploy.yml` を `ci.yml` に改名し、`pull_request` でも起動する。** `build` ジョブ
   （`npm ci` → `npm test` → `npm run docs:build` → 成果物のアップロード）はどちらの
   イベントでも走り、`deploy` ジョブだけ `pull_request` 以外のときに動く。
2. **`main` に Ruleset を作る。** PR 経由のみ、`build` チェックが緑でないとマージできない。
   直接 push も同じ Ruleset で止める。
3. `CONTRIBUTING.md` の手順とガードレール表を実態に合わせる。

手順の詳細は [`ci.yml`](../../.github/workflows/ci.yml) と `CONTRIBUTING.md` が所有する。

## 理由

**検査手順を1か所に置きたい。** PR 用と公開用でファイルを分けると、ステップを直すとき
片方だけ直す事故が起きる。「PR で緑だったのに公開で落ちる」は、この二重管理から生まれる。
1ファイルでイベントだけ分ければ、PR で走った手順がそのまま公開でも走る保証になる。

**Ruleset を足すのは、CI だけでは止まらないから。** チェックが付いても、マージ可能の
判定に使われなければ赤いまま merge できる。サーバー側で「`build` 必須」と決めて初めて
フックの掛け忘れや `--no-verify` に依存しない守りになる。

受け入れたコスト:

- PR のたびに Pages の成果物までアップロードする（数十秒・数 MB）。deploy ジョブを
  分岐させるより、`build` を完全に同一に保つことを優先した
- Ruleset の作成は GitHub 側の設定で、リポジトリのファイルには残らない。存在は
  `gh api repos/{owner}/{repo}/rulesets` で確認する
- Ruleset は「`build` という名前のチェック」に依存する。ジョブ名を変えたら Ruleset も直す

## 検討した代替案

| 案 | 内容 | 却下理由 |
|---|---|---|
| A（採用） | 1ファイルで `pull_request` と `push` を受け、`deploy` だけ条件付き | — |
| B | PR 用に `check.yml` を別に足し、test + build を書く | 手順が二重になる。4ステップとはいえ、片方だけ直す事故の温床 |
| C | 手順を `workflow_call` の再利用ワークフローに切り出し、両方から呼ぶ | 4ステップに対して仕組みが重い。ファイルが3本になり読む側の負担が増える |
| D | Ruleset だけ作り、CI は足さない | 「PR 必須」は守れるが、赤いままのマージは止まらない。Issue の目的を満たさない |

## 結果（この決定が生むもの）

- PR を開くと `build` チェックが付き、赤いあいだはマージできない
- `main` への直接 push はサーバー側でも止まる（pre-push フックとの二重防御）
- `CONTRIBUTING.md` の記述と実態が一致する
- 宿題: Ruleset は手で作る設定なので、リポジトリを作り直したときは再作成が要る
